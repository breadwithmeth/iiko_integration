# Автоматизация бонуса операторов за продажу блюд кухни

## Суть

Бонус считается **на лету** из уже имеющихся в локальной БД данных (`Order → OrderItem → Product → ProductGroup`), по образцу существующих эндпоинтов `/api/orders/stats` и `/api/orders/upt-kpi`. **Изменений схемы Prisma не требуется** — категории определяются динамически из номенклатуры iiko (вариант, который вы выбрали).

## Логика расчета (новый сервис `KitchenBonusService.ts`)

**Определение категорий:**
- Корневая группа ищется в `ProductGroup` по имени из новой env-переменной `KITCHEN_ROOT_GROUP_NAME` (по умолчанию `«Кухня»`).
- Кухонные категории = прямые дочерние группы корня («Закусочки для старта», «Гарниры» и т.д.).
- Категория позиции: идем вверх по цепочке `Product.parentGroupId` (поддержка вложенных подгрупп); если в цепочке встречается прямая дочерняя группа «Кухни» — позиция кухонная, категория = эта группа.
- Если корневая группа «Кухня» не найдена — эндпоинты возвращают пустые отчеты + флаг `warning`, чтобы это было видно в UI (никаких падений).

**Расчет по заказу** (статусы `CREATED` и `CLOSED` — успешные; `CANCELLED`, `FAILED`, `DRAFT`, `SUBMITTING`, `UNKNOWN` исключены):
- `categories` = множество уникальных кухонных категорий среди позиций заказа
- `kitchenSum` = Σ(price × amount) только кухонных позиций (в копейках; модификаторы позиции не входят в базу — база строго по позициям группы «Кухня»)
- `percent` = `min(кол-во уникальных категорий, 5)`, если категорий ≥ 1, иначе 0 (5 стейков = 1 категория = 1%; количество единиц внутри категории процент не увеличивает; 6 категорий = максимум 5%)
- `bonus` = `round(kitchenSum × percent / 100)` — копейки, округление до копеек

## Backend (новый модуль `apps/api/src/modules/bonus/routes.ts`)

Регистрируется в `app.ts` после `orderRoutes`. Авторизация: `app.authenticate`; OPERATOR принудительно видит только свои данные (переопределить `operatorId` из JWT нельзя).

| Эндпоинт | Назначение |
|---|---|
| `GET /api/bonus/orders?dateFrom&dateTo&operatorId` | Детальный отчет: `{ createdAt, externalNumber, operator: {name}, categories: string[], uniqueCategories, kitchenSum, percent, bonus }` — только заказы, где есть кухня |
| `GET /api/bonus/operators?dateFrom&dateTo&operatorId` | Сводный: `{ operator: {id,name}, ordersWithKitchen, kitchenSalesTotal, bonusesTotal, payoutTotal }` |
| `GET /api/bonus/categories` | Диагностика: найдена ли корневая группа и список категорий (для вывода в UI) |

Фильтр периода — по `createdAt`, тот же паттерн, что в stats/upt-kpi (сегодня/7 дней/месяц/квартал/произвольный).

## Frontend (новая страница `apps/web/src/pages/BonusPage.tsx`, маршрут `/bonus`)

- Скелет по образцу `UptKpiPage.tsx`: пресеты периода + произвольный период, фильтр по оператору (только ADMIN, список из `/api/users`), две вкладки: **«По заказам»** (детальная таблица со всеми 8 колонками из ТЗ) и **«По операторам»** (сводная ЗП-таблица: ФИО, заказов с кухней, сумма продаж кухни, сумма бонусов, итого к выплате).
- Карточки-итоги: сумма продаж кухни, сумма бонусов, кол-во заказов с кухней.
- Экспорт CSV обеих таблиц — клиентский Blob с BOM, как в `UptKpiPage.tsx:267`.
- Плашка с активными кухонными категориями (из `/api/bonus/categories`) + предупреждение, если группа «Кухня» не найдена.

Сопутствующие правки: `hooks.ts` (useBonusOrders/useBonusOperators/useBonusCategories + типы), `router.tsx` (маршрут `/bonus`), `AppLayout.tsx` (пункт меню «Бонусы кухни» — виден всем ролям), стили по аналогии с существующими классами.

## Тесты (Vitest)

1. `apps/api/src/test/kitchenBonus.test.ts` — юнит-тесты чистой логики: все пороги 0–5 категорий; кап на 5% при 6 категориях; 5 стейков = 1%; база только из кухонных позиций (не-кухонные товары не входят в базу и в %); позиции без product/группы игнорируются; округление до копеек; вложенные подгруппы через цепочку родителей.
2. Тест роутов в стиле `routes.integration.test.ts` (mock prisma через `vi.mock`): DETAIL и SUMMARY отдают ожидаемые структуры; OPERATOR видит только свои заказы; фильтр статусов.

## Допущения (зафиксированы вашими ответами)

1. Статусы в расчете: `CREATED + CLOSED` (отмененные/ошибочные исключены).
2. Категории — динамически, подгруппы группы «Кухня» из iiko.
3. Отчеты: веб-страница + CSV.
4. Доступ: ADMIN видит всё, оператор — только свои строки.
5. Бонус нигде не «запирается» в момент создания — отчет всегда пересчитывается по актуальной конфигурации категорий, что исключает расхождения при изменении меню в iiko.

Проверка: `npm test` в `apps/api`, запуск dev-серверов и визуальная проверка страницы `/bonus` на реальных данных.
